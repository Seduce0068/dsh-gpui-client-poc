## 結論

- **機能バグではない。** チャンクの結合順・区切りなし・セッション別
  分離は既存テストで保証されており、誤表示やデッドロックは生じて
  いない。
- **性能・堅牢性の改善課題ではあるが、通常の回答長では影響は小さい。**
  深刻化するのは、極端に細かいチャンク、非常に長いストリーム、
  新規データなしの再描画が繰り返される場合に限られる。
- 旧 investigation の「100 ms ポーリング + `chunks.join("")`」という
  記述は現行コードと不一致である。現行は `Notify` 駆動の描画に
  置換済みであり、本報告は現行コードを対象に再評価した。

## 静的解析（対象コード）

`src/bin/acp_stream_ui.rs` の該当箇所は次のとおり。

- 130-143 行: `sessions: HashMap<SessionId, Vec<String>>` へ
  `append_update()` が上限なしで `push` する。
- 147-152 行: `session_transcript()` が呼び出しごとに
  `chunks.concat()`（旧 `join("")` と等価）で新規 `String` を生成。
- 157-175 行: `render_transcript()` もセッション単位で
  `chunks.concat()` を実行し、全体をさらに `push_str` で構築。
- 262-291 行: `Render::render()` が `Mutex` を保持したまま
  `render_transcript()` を呼ぶ。再結合は UI スレッドで実行され、
  同時に producer 側の `append_update()` もブロックする。
- 298-307 行: `record_notification()` が空でない全行を蓄積し、
  バイト数・件数の上限は存在しない。
- 309-363 行: `StreamSignal`（`Notify` + `CancellationToken`）が
  旧 100 ms ポーリングを置換。通知ごとに `changed()` が呼ばれる。
- 440-451 行: ACP 通知ハンドラが `record_notification()` の後に
  `signal.changed()` を発火し、再描画を要求する。

帰結として、1 回の再描画のコストは「その時点までの全チャンクの
バイト総和」に比例する。描画回数を K、チャンク数を N とすると
累積コストはおおむね O(K × 総バイト数) であり、K が N に比例する
（チャンク到着ごとに描画される）状況では O(N^2) に近づく。

- OS: Linux <kernel-version> x86_64（`uname -a`）
- CPU: 汎用デスクトップCPU（`/proc/cpuinfo`）
- メモリ: 数十 GiB 合計 / 十分な空き容量（`free -h`）
- コンパイラ: rustc 1.88.0 / cargo 1.88.0（リポジトリの
  `rust-toolchain.toml` と一致）
- 計測方法: 依存なしの純 Rust プログラムを
  `rustc -O --edition 2021` でビルドし、`std::time::Instant` で計測。
  一時スクリプトは `/tmp/perf_probe.rs` に置き、リポジトリには
  残していない。既存コードは一切変更していない。

### 方法

- シナリオ A（現行相当）: 32 バイトのチャンクを `Vec<String>` に
  `push` するたびに `chunks.concat()` を呼び、結果を
  `std::hint::black_box` して最適化による除去を防止。
- シナリオ B（比較対象）: 単一 `String` へ `push_str` で追記する
  増分方式。同じ最終バイト数を生成することを `assert_eq!` で確認。
- 補助計測: 最終サイズを 64 KiB に固定したままチャンク粒度を
  4〜1024 バイトで変化させ、粒度の影響を分離。

### 結果

```text

4000    約 0.028   約 0.000006     約 4300x   128000
8000    約 0.093   約 0.00013      約 740x    256000
```

### 解釈

- N を 1000 から 32000（32 倍）に増やすと累積再結合時間は
  約 0.0014 秒から約 1.43 秒（約 1000 倍）へ増加した。
  32 の 2 乗と同オーダーであり、O(N^2) 仮説と整合する。
- 増分方式は同範囲で 0.6 ミリ秒以下に留まり、線形かつ無視できる
  水準だった。差は 3 桁以上。
- 最終サイズを固定しても、チャンクを 1024 バイトから 4 バイトへ
  細分化すると再結合時間は約 0.00004 秒から約 0.37 秒（約 250 倍）
  に増えた。バイト総量だけでなく粒度がコストを支配する。
- 実用的なレンジでの外挿（推論、未実測）: 1000 チャンク程度の
  典型的な回答なら累積コストは数ミリ秒で問題にならない。
  32000 チャンク・約 1 MiB の回答でも累積 1.4 秒は書き捨て
  作業であり、1 フレームあたりの再結合は数十〜百マイクロ秒
  程度と見積もられる。したがって**通常利用で体感劣化は起きにくい**。

## 機能バグか性能課題か

- 分類: **性能課題 / DoS 堅牢性の改善項目**であり、機能バグではない。
- 根拠: 結合結果の一致性 (`agent_message_chunk_join_is_unchanged`,
  `single_session_render_is_legacy_verbatim_join`) とセッション分離
  (`concurrent_sessions_do_not_share_a_transcript`) のテストが存在し、
  現行コードはこれらを満たす。誤った文字列や混線は観測されていない。
- 既存トリアージとの対応: round-3 A-3 `unbounded-chunk-buffer-dos`
  [改善/medium/high/no]、round-1 A-7 / B-18、round-5 E5B-03
  [バグリスク/medium/no] と同一系統。本計測は「実 exploit は未実行」
  だった項目に小規模な定量根拠を補うもので、深刻度の引き上げは
  支持しない。
- 注意点: `Render::render()` が `Mutex` 保持中に全結合を行うため、
  transcript が極端に大きい場合は再描画が producer の追記を
  待たせる。これはレイテンシの問題であり、正確性の問題ではない。

## 推奨対応（未実装・コード変更なし）

- セッションごとに追記用 `String` を保持し、`append_update()` 時に
  `push_str` する増分方式へ変更。描画時は必要ならスナップショット
  を返すだけで全チャンクの再結合を避ける。
- チャンク件数またはバイト総和に上限を設け、リングバッファまたは
  予算超過時の backpressure / 省略表示を導入する。
- `Render::render()` では `Mutex` から必要な値だけを短時間で
  スナップショットし、ロック外で文字列を組み立てる。

## 未確認点

- 実 GPUI での再描画頻度とバッチングは未計測。通知がバーストした
  際に `Notify` の permit が蓄積して K > N になり得るかも未検証。
- 実際の `dsh --profile acp` が出力するチャンク数・サイズの分布を
  実データで取得していない（モデル残高・接続環境に依存）。
- メモリ使用量は静的推算のみ（32 バイトペイロード + `String`
  ヘッダ約 24 バイト × N）で、実 RSS は計測していない。
- ベンチマークは純粋な `concat()` / `push_str()` の代理計測であり、
  GPUI の `SharedString` 変換やアリーナ確保コストは含まない。
- CPU ピニングなしの単一環境・2 回実行（2 回目の数値を採用）であり、
  アロケータノイズによるばらつきがある。厳密な統計処理は未実施。
